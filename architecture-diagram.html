Prelude Health · System Architecture

From booking wizard to physician PDF — the full agentic pipeline

A patient books, an SMS link arrives, and a fresh Strands BidiAgent is spun up per call to speak with them live over AWS Bedrock Nova 2 Sonic. A second, separate agent then turns the finished call into a structured report.

Agentic tool belt, in full

The only things the model can actually do — everything else is just talk.

  • navigate_to_screen / get_current_screen — enforces screen order and refuses to advance a screen with unanswered required fields.
  • record_intake_details — writes an answer into a fixed-field screen (medication, allergies, history…).
  • start_prescreening → ask_symptom_question / record_symptom_answer — a model-written, one-question-at-a-time loop bounded to 7–10 questions.
  • cancel_appointment, offer_appointment_times, move_appointment — in-call rebooking.
  • request_document_upload — prompts the patient for a photo/scan without blocking the call.
  • end_session — the model's own way to hang up; backed by an 8-second watchdog that ends the call anyway.

REST surface, by concern

Everything sits under /api/v1 except the socket, which is deliberately outside it.

  • Booking — /booking (catalog), /mock-booking (demo scheduling), /webhooks (real scheduling-platform inbound).
  • Session — /sessions/* attach, consent, appointment reschedule, ws-ticket minting.
  • Doctor — /doctors/* registration + Google OAuth callback.
  • Reports & uploads — physician report (API-key gated), the ungated report-download-url demo lookup, document/recording upload URLs.
  • Live call — /ws/intake/{session_id}, mounted outside /api/v1 on purpose.

Data & storage

Two stores, cleanly split by shape.

  • MongoDB Atlas — session_chat_history, doctors, doctor_registrations, prescreening_question_bank, appointment_slots, scheduling_events, sweeper_locks, ws_tickets.
  • Amazon S3 — reports/{id}/report.pdf, patient-uploaded documents, call recordings — all via presigned URLs, never proxied through the API.
Security surface, kept off the main diagram for clarity: three HMAC-SHA256 tokens — intake (long-lived, in the SMS link), session (HttpOnly cookie, issued at attach), ws (short-lived, single-use nonce) — are the same signing scheme with the purpose baked into the signature, so one can't be replayed as another. The physician's own report additionally requires an X-API-Key header; the patient-facing report-download-url deliberately does not, by design, for the session-id lookup flow.
